# 이미지

## 생성 전에 정할 것

`direction.md`의 이미지 목록에 이미지마다 네 가지를 정한다.

- **파일명**
- **놓일 곳**: 섹션과 화면에서 차지하는 크기
- **비율**: 레이아웃 칸에 맞춘다(16:9, 3:2, 4:5, 1:1 등)
- **보여 줄 정보**: 그 이미지가 없으면 고객이 모르게 되는 것

정보가 없는 이미지는 만들지 않는다.

- 히어로에 카피를 올린다면, 카피가 앉을 빈 면(벽, 바닥, 하늘)의 위치를 프롬프트에 적는다. 그게 어려우면 카피를 이미지 옆에 둔다.
- 휴대폰에서 잘려도 되도록 피사체를 가운데 2/3 안에 둔다.

## 일관성

- **스타일 블록 하나를 모든 프롬프트 끝에 붙인다.** 블록에는 다음을 적는다.
  - 공간: 장소, 재질, 색
  - 빛: 시간대, 방향
  - 카메라: 높이, 렌즈 느낌
  - 색감
  - `no text, no letters, no logo, no watermark`
- **같은 피사체가 여러 장에 나오면 첫 결과를 다음 장의 참조 이미지로 넣는다.** 같은 집, 같은 동물, 같은 제품이 해당한다. 참조 이미지를 받는 모델을 쓴다.
- **전후 비교는 한 장을 기준으로 다른 한 장을 편집해서 만든다.** 보통 '후'를 먼저 만들고, 그 이미지를 입력으로 '전'을 만든다. 구도, 빛, 카메라를 그대로 두라고 명시한다. 두 장은 같은 크기로 맞춘다.

## Higgsfield

- 설치된 Higgsfield MCP의 이미지 생성 도구를 직접 호출한다.
- 모델은 `models_explore`로 확인해 고른다. 사실적인 사진에 강한 모델을 쓰고, 참조 이미지 편집이 필요하면 편집을 지원하는 모델을 쓴다.
- 서로 독립적인 이미지는 함께 제출해도 된다. 배치 도구를 쓰거나, 이미지 생성만 맡긴 subagent를 쓴다.
- 받은 파일은 직접 열어 본다. 확인할 것은 다음과 같다.
  - 손과 발 모양, 이미지 안에 생긴 글자
  - 피사체 위치
  - 정한 정보가 보이는지
- 슬롯당 재생성은 1회까지다. 두 번째 결과도 맞지 않으면 레이아웃을 이미지에 맞춘다.
- 결과를 모르는 제출(타임아웃, 끊김)은 다시 제출하지 않는다. job ID로 조회하거나 최근 생성 목록을 한 번 확인한다. 상태를 반복 조회하지 않는다.
- 예산은 PRD나 design의 수량이 우선이다. 수량이 없으면 12장 이하로 하고, 재생성도 1장으로 센다. 영상은 입력이 요청할 때만 만든다.

## 파일

- 원본은 run 디렉터리 `assets/<파일명>`에 저장한다. 페이지에서 원격 URL을 직접 참조하지 않는다.
- 웹용 사본은 `app/` 안 이미지 폴더에 둔다. 긴 변 2400px 이하, 품질 80 안팎으로 만든다.

```sh
sips -Z 2400 -s format jpeg -s formatOptions 80 assets/hero.png --out app/public/img/hero.jpg
cwebp -q 80 -resize 2400 0 assets/hero.png -o app/public/img/hero.webp   # cwebp가 있을 때
sips -Z 1200 -s format jpeg -s formatOptions 78 assets/hero.png --out app/public/img/hero-1200.jpg  # 휴대폰용 srcset
```

- `<img>`에 넣을 것
  - `width`와 `height`(비율 고정)
  - alt
  - 첫 화면 밖 이미지는 `loading="lazy"`, 히어로는 `fetchpriority="high"`
- alt는 이미지가 전달하는 정보를 한 문장으로 쓴다. "사진", "이미지"로 시작하지 않는다.
- 입력이 연출 이미지 고지를 요구하면 정한 문구를 그대로 쓴다.

## media-receipts.json

`assets/media-receipts.json`은 제출 기록이자 예산 장부다. 다음 규칙을 지킨다.

- 호출 직전에 항목을 `submitting`으로 먼저 저장한다. 응답을 받으면 상태를 고친다.
- 태스크가 다시 시작되면 이 파일을 먼저 읽는다. `submitting`, `completed`, `unknown`인 슬롯은 다시 제출하지 않는다.
- job ID, 모델, 상태는 도구가 돌려준 값만 쓴다.
- sha256은 `shasum -a 256 <원본>`으로 계산한다.

```json
{
  "budget": { "images": 8, "videos": 0, "source": "prd" },
  "items": [
    {
      "file": "assets/hero-after.png",
      "purpose": "청소를 마친 거실에 아침 빛이 드는 모습",
      "placement": "hero",
      "model": "<도구가 돌려준 모델>",
      "job_id": "<실제 job ID>",
      "status": "completed",
      "sha256": "<원본 해시>"
    }
  ]
}
```

`status`는 `submitting`, `completed`, `failed`, `unknown` 중 하나다. `failed`나 `unknown`이면 `reason`을 적는다. 실제 제출한 모든 시도는 실패·결과 미확인·재시도를 포함해 예산에 센다. 제출 전 검증에서 거절되어 생성 요청이 전송되지 않았음이 확인된 경우에만 예산에서 뺀다.
